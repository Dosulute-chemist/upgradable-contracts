# Upgradable Contracts

This is my work on upgradeable smart contracts. I looked into three ways of doing it, which are UUPS, Transparent Proxy and the Diamond standard, and then built a small contract for each one and tested everything in Remix.

The idea behind all of them is simple. Once a contract is deployed you can't change its code, so you deploy a proxy instead. People always interact with the proxy's address, and the proxy passes each call to a separate logic contract. When I want to change something, I deploy a new logic contract and point the proxy at it. The address stays the same and so does all the stored data.

## What's in the repo

Everything lives inside the UpgradeableContracts folder. The UUPS voting contract is in `votinguups.sol`, the Transparent proxy lending contract is in `lending.sol` inside the transparent folder, and the Diamond with ERC-20 and ERC-721 is in `diamond.sol` inside the Diamond folder. The artifacts folders were generated by Remix when I compiled, so they just hold the compiled output. The transparent and Diamond folders ended up inside the uups folder because of how I saved them in Remix. It doesn't change how anything works.

## How the three patterns compare

With UUPS, the upgrade function lives inside the logic contract itself. That keeps the proxy light and cheap, but it comes with a risk. If you upgrade to a version that forgot to include the upgrade function, you can never upgrade again. So I made sure `_authorizeUpgrade` is there and that only the owner can call it.

With the Transparent proxy, the upgrade function lives in a separate contract called `ProxyAdmin`. The proxy checks who is calling every time, which costs a bit more gas, but admin actions and normal user actions stay completely separate.

The Diamond works differently. Instead of one logic contract it has lots of small ones called facets, plus a table that says which function belongs to which facet. Because of that I can add, swap or remove a single function without touching the rest. It also gets around the 24 KB contract size limit.

## Running it in Remix

Go to https://remix.ethereum.org and add the three contract files. In the Solidity compiler tab, pick version 0.8.28 and compile. Remix pulls in the OpenZeppelin imports on its own. Then in the Deploy tab, set the environment to Remix VM (Cancun).

One thing to remember for all three: always use the proxy (or diamond) address when you interact with the contract, never the address of the logic contract.

## 1. Voting contract (UUPS)

`VotingV1` lets the owner create proposals, and anyone can vote yes or no, once per proposal. Proxies can't use constructors, so there is an `initialize()` function that runs one time instead. The constructor calls `_disableInitializers()` so nobody can initialize the logic contract directly.

`VotingV2` is the upgrade. It adds `closeProposal`, and once a proposal is closed nobody can vote on it. I only added new variables at the end and left the old ones alone, because changing the storage order in an upgrade would scramble the data.

To test it, I first deployed `VotingV1`. Then I deployed `ERC1967Proxy`, giving it the VotingV1 address and `0x8129fc1c` as the data, which is just the encoded call to `initialize()`. I loaded `VotingV1` at the proxy address using "At Address", created a proposal and voted on it. After that I deployed `VotingV2` and called `upgradeToAndCall` on the proxy with the V2 address and `0x`. Finally I loaded `VotingV2` at the same proxy address. `version()` said V2, the old votes were still there, and `closeProposal` worked.

## 2. Lending contract (Transparent proxy)

`LendingV1` is a basic ETH lending pool. You deposit ETH as collateral and can borrow up to half of what you put in. You can repay, and you can withdraw only the part of your deposit that isn't backing a loan. I added a small reentrancy guard and made sure balances are updated before any ETH is sent out.

`LendingV2` adds a borrow fee, set in basis points, so 100 means 1%. The fee gets added to what the borrower owes. Deposits and debts from V1 carry over unchanged.

To test it, I deployed `LendingV1`, then deployed `TransparentUpgradeableProxy` with the LendingV1 address, my own account as the initial owner, and `0x8129fc1c` as the data. The proxy creates its own `ProxyAdmin`, and I found its address in the logs of the deploy transaction, under the `AdminChanged` event (`newAdmin`). I loaded `LendingV1` at the proxy address and tried deposit, borrow, repay and withdraw. Then I deployed `LendingV2`, loaded `ProxyAdmin` at its address and called `upgradeAndCall` with the proxy address, the V2 address and `0x`. After loading `LendingV2` at the proxy address I called `setBorrowFee(100)`. The old balances were still correct and new loans included the fee.

## 3. Diamond with ERC-20 and ERC-721

The diamond is made of several facets. `DiamondCutFacet` is how the diamond gets upgraded, by adding, replacing or removing functions, and only the owner can use it. `DiamondLoupeFacet` has read-only functions for looking at what the diamond contains. `OwnershipFacet` shows and transfers the owner. `ERC20Facet` is a normal token with a `mint` that only the owner can use, and `ERC721Facet` is an NFT collection with a `mintNFT` that only the owner can use.

Each facet stores its data in its own storage slot, so the token data, the NFT data and the diamond's own routing table can't overwrite one another.

Setting up a diamond by hand means encoding a long list of function selectors, which is a pain. So I wrote a `DiamondDeployer` contract that does the whole setup in one transaction. It deploys the diamond and the facets, registers every function, sets the token and NFT names, and then gives ownership to my account.

To test it, I deployed `DiamondDeployer` and read the `diamond` getter to get the diamond's address. I loaded `ERC20Facet`, `ERC721Facet`, `OwnershipFacet` and `DiamondLoupeFacet` at that address. Then I minted some tokens and an NFT, transferred both, and called `facetAddresses()` to check that all five facets were registered.

### The problem with ERC-20 and ERC-721

This was the trickiest part. Both standards have `balanceOf(address)`, `approve(address,uint256)` and `transferFrom(address,address,uint256)`, with exactly the same signatures. A diamond can only send a given function to one facet, so both standards can't use those names in the same diamond.

My fix was to keep the standard names for ERC-20 and rename the NFT versions to `nftBalanceOf`, `nftApprove` and `nftTransferFrom`. For the same reason the collection name and symbol come from `collectionName()` and `collectionSymbol()`. The downside is that the NFT side won't be fully recognised by outside tools like marketplaces. That is a genuine limitation of putting these two standards in one diamond, and I would rather say so than hide it.

## Security

The logic contracts call `_disableInitializers()`, and `initialize()` can only run once. In all three projects only the owner can upgrade: for UUPS that is `_authorizeUpgrade`, for the transparent proxy it is the `ProxyAdmin` owner, and for the diamond it is `diamondCut`. Minting in the diamond is owner-only too. Every V2 contract inherits from V1 and only adds variables at the end, so the stored data stays valid after an upgrade.

This is a learning project and hasn't been audited, so please don't use it with real money.
